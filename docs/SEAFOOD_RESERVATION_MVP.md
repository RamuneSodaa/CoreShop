# Seafood Reservation MVP（卖鱼接龙版）

## 目标

把微信群里的人工接龙改成：鱼货展示 → 顾客选择数量 → 填写称呼/取货方式 → 提交预订 → 原子占用库存 → 后台查看预订。

本阶段明确 **不接微信支付**。货款继续由顾客按微信群原方式微信转账，管理员线下确认。

## 当前核心流程

### 1. 今日鲜鱼首页

- 首页直接读取所有已上架商品，并读取默认货品的实时可售库存。
- 每种鱼显示：图片、鱼名、简介、会员价、非会员参考价、剩余库存和单位。
- 顾客可在首页直接 `- / +` 选择数量，不需要逐个进入商品详情。
- 底部实时汇总已选种类、数量和预计金额。
- 预订栏已避开 CoreShop 原商城 TabBar，H5 / 小程序均可正常操作。

### 2. 不再强制商城登录或手机号授权

旧流程“登录 → AddCart → 商城确认订单”已经从鲜鱼首页移除。

点击“提交预订”后，页面直接弹出轻量预订表单：

- 称呼 / 微信名（必填）
- 取货方式：到店取 / 邮寄（必填）
- 联系方式（选填）
- 备注（选填）

不要求手机号授权，不要求商城账号，不唤起微信支付。

### 3. 独立鲜鱼预订 API

新增公共接口：

- `POST /Api/SeafoodReservation/Create`：创建预订并占用库存
- `POST /Api/SeafoodReservation/Get`：凭随机 `lookupToken` 查询单笔预订

接口使用独立数据表：

- `SeafoodReservation`
- `SeafoodReservationItem`

表由 SqlSugar CodeFirst 首次访问接口时自动创建。

### 4. 并发库存保护

创建预订时不相信前端库存值，而是在数据库事务内再次检查。

每个货品通过单条条件 UPDATE 完成：

`freezeStock = freezeStock + quantity`

同时要求：

`stock - freezeStock >= quantity`

因此多人同时接龙时，只有仍有足够可售库存的请求能够成功；任意一项失败则整个事务回滚。

CoreShop 商品详情返回的 `product.stock` 已经是 `总库存 - freezeStock` 后的可售库存，所以预订成功后首页刷新会自动看到剩余库存下降。

### 5. 防重复提交

前端每次确认预订生成 `requestId`。服务端若发现相同 `requestId` 已创建预订，会返回原预订结果，减少重复点击或网络重试造成的重复占库存风险。

## 当前测试商品

- 商品：野生大龙利
- goodsId：4158
- productId：4679
- 单位：斤
- 价格：39.50 元/斤
- 初始库存：30
- 初始冻结库存：0

目标验证：预订 3 斤后，可售库存从 30 变为 27。

## 当前约束

- CoreShop 原生商品库存仍为整数，本阶段按 `1斤 / 2斤 / 3斤`、`1条 / 2条` 使用。
- 当前“我的预订”先使用本机 storage 保存最近预订号和 lookupToken；正式微信小程序上线后再接入 OpenID 作为稳定身份。
- 当前仍保留 CoreShop 其他商城页面和后台功能，后续会逐步隐藏不需要的支付、优惠券、积分、分销、拼团等入口。
- 当前改动仍在 `seafood-reservation-mvp` 分支，未合并 `master`。
